# TU-499 석박통합 로그인

## 결정 및 기존 정책

- 사용자가 SSO `kaist_v2_info.std_prog_code`의 문자열 `"7"`을 석박통합으로 처리하도록 확정했다.
- `student_enum` 테이블은 존재하며 조회 시 `1=학부생`, `2=석사생`, `3=박사생`이 있고 `id=4` 행은 없었다.
- `student_t`에는 학위 값 `4`인 과거 기록 64건(50명)이 있었다. 전부 학번 8000대이고 2023~2024년 학적이며, 현재 유효한 기록은 0건이다. 이 과거 기록의 의미를 정의한 코드표는 확인하지 못했으며 이번 작업에서 값을 변경하지 않는다.
- 로그인은 이 테이블을 읽어 동적으로 판정하지 않는다. `student_t.student_enum`은 정수이며 Prisma에서 enum 테이블에 대한 relation은 없다.
- 기존 테이블과 relation을 유지하고 `4=석박통합생`을 추가한다. 다른 SSO 코드나 학번 구간을 새로 추정하지 않는다.

## API 계약

| 위치 | 추가 항목 |
| --- | --- |
| 로그인 학적 | SSO `"7"` → `student_t.student_enum = 4` |
| 사용자 프로필 | `masterDoctor: { id, number }` |
| `POST /auth/refresh` 응답 | `accessToken.masterDoctor?: string` |
| 사용자 전환 응답 | 동일한 `accessToken.masterDoctor` |
| access JWT | `type: "masterDoctor"`, `studentId`, `studentNumber` |
| 화면 표시 | 석박통합과정 / Integrated Master's and PhD |

기존 응답 필드를 유지하고 새 optional 필드를 추가한다. 학생 권한 목록은 공통 상수로 공유하며 석박통합도 일반 학생으로 처리한다. 학부생 전용 권한과 HP 학번 제한은 유지한다.

## 처리 흐름

1. SSO `"7"`을 받으면 현재 학적의 존재 여부와 관계없이 학위 `4`로 저장한다.
2. 로그인·갱신·사용자 전환에서 학위 `4`를 `masterDoctor` 프로필과 토큰으로 전달한다.
3. 브라우저는 이 토큰만 있어도 로그인할 수 있고, 프로필 선택 및 학생 기능에서 사용할 수 있다.
4. 지원하지 않는 다른 SSO 코드는 기존의 현재 학적 조회 및 학번 fallback 정책을 따른다.

## 배포

1. [enum 추가 SQL](TU-499-add-master-doctor-enum.sql)을 먼저 적용한다. 기존 `id=4`가 있으면 INSERT가 실패하므로 그 의미를 확인한다.
2. `masterDoctor`를 인식하는 프론트엔드와 API를 배포한다. 프론트엔드를 먼저 배포하면 이전 API와도 호환된다.
3. 기존 로그인 세션은 새로고침 또는 재로그인한다. 새 SSO 로그인에서 확인된 학적을 갱신하며 과거 기록을 일괄 변경하지 않는다.

운영 DB 변경과 배포는 이 작업에서 실행하지 않는다.

## 검증

- SSO `"7"`, 학번 끝자리 `8083`, 현재 유효 학적 없음 → 로그인 및 학적 저장 성공.
- 기존 박사 학적에서 SSO `"7"` 수신 → 석박통합으로 갱신.
- DB의 학위 `4`가 프로필·토큰 갱신·사용자 전환에서 보존됨.
- 학생 기능 및 전화번호 처리 허용, 학부생 전용 기능 차단.
- 석박통합 단독 토큰 선택, 화면 표시 및 기존 프로필 선택 순서 회귀 검증.
- 실제 MySQL 통합 테스트, API/web 빌드, 변경 코드 가드 및 MC/DC.
